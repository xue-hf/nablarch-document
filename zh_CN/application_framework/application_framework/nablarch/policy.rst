.. _nablarch_architecture-no_input:

对外部接收的未输入值的处理方式
--------------------------------------------------
应用需要接收来自外部的各种数据，包括未输入的值。
未输入值通常有两种表示方式：``null`` 和空字符串。
如果应用开发者需要同时考虑这两种表示方式，容易导致实现错误，并可能引发意外故障。
为避免此类问题，必须统一未输入值的处理方式。

为了统一未输入值的表示方式，Nablarch 将未输入值转换为 ``null``。
例如，来自外部的输入数据，如 HTTP 请求参数或 XML 中的未输入值，都会被转换为 ``null``。
此外，当通过自定义标签或格式化输出等方式向外输出 ``null`` 时，会根据输出数据格式将其转换为表示“未输入”的相应值。
这些转换由 Nablarch 的handler和库自动完成，因此应用无需自行处理未输入值的转换。
但需要注意的是，若要将未输入值转换为 ``null``，必须在handler队列中添加 :ref:`normalize_handler`。

根据此原则，应用开发中应统一将未输入值视为 ``null`` 进行处理。

返回集合或数组的API原则上不返回null
--------------------------------------------------
Nablarch提供的返回集合或数组的API，在没有目标数据的情况下，原则上返回空集合或空数组，而不是 ``null``。
通过这种方式，可以防止调用方因 ``null`` 引用导致的问题，同时减少条件分支，提高代码可读性。

例如，在视图（JSP）中以列表形式显示数据库查询结果时，无需进行 ``null`` 判断，可直接进行循环处理，从而提高代码可读性。
如果必须考虑 ``null``，则在JSP中需要编写分支逻辑，或在服务器端将 ``null`` 的集合放入请求域，导致冗余代码增多，同时也容易引发实现错误。

另外，对于通过指定标识符获取数据的API（如HTTP请求参数），则返回 ``null``，而不是空数组。

Nablarch不抛出受检异常
--------------------------------------------------
Nablarch内的所有API仅抛出非受检异常。此外，Nablarch中定义的异常类也全部为非受检异常。
通过全部使用非受检异常，应用程序无需显式处理异常，可以在处理器（handler）中统一进行异常处理。

另外，受检异常存在以下缺点：

* 如果不捕获异常，或不在 ``throws`` 中声明，会导致编译错误。
  如果选择捕获异常，则需要在各处重复实现类似的异常处理逻辑。

* 每当抛出的异常增加时，会影响应用程序的代码。
  此外，影响范围广泛，例如需要在所有调用链中的方法上都添加 ``throws`` 声明。

日志与异常的消息统一为英语
--------------------------------------------------
因为认为Nablarch会在日本以外的地区也有使用，因此日志与异常的消息统一为英语。
除此以外，Nablarch未提供将内部输出的日志及异常消息更改为英文以外语言的功能。

可以通过替换组件更改Nablarch生成的SQL
----------------------------------------------------------------------------
在Nablarch中，所有访问数据库的组件都定义了接口，因此可以替换其实现。
这是因为允许项目方创建实现类，并通过配置文件替换组件，从而能够更改生成的SQL。

由此，例如当需要增加或删除Nablarch所使用的表的列时，可以通过替换组件来应对。

此外，如果只是想将表名或列名从默认值修改，无需创建新类，仅修改配置文件即可。

不使用开源代码
--------------------------------------------------
Nablarch的生产代码不使用开源代码，目的是在发现严重缺陷或漏洞时，能够快速修复并发布。

不过，对于使用开源代码能带来优势的场景，Nablarch提供了可使用开源代码的组件作为 :ref:`adaptor`，可根据项目需求选择采用。

发生多个异常时抛出起因异常
--------------------------------------------------
在处理过程中发生异常，后续处理中又发生另一个异常时，会存在多个异常。
在这种情况下，对问题解决最关键的是起因异常，因此Nablarch会抛出起因异常。
同时，为便于调查其他异常，其余异常的信息将输出到WARNING日志中。

线程安全
--------------------------------------------------
Nablarch提供的功能基本上是线程安全的。
这是因为Nablarch采用在handler队列上由各线程执行handler来处理请求的架构。详细架构请参见 :ref:`架构章节 <nablarch_architecture>`。
由此，在Web应用等各线程处理客户端请求的环境中，也能安全地处理请求并返回结果给客户端。

此外， :ref:`repository` 中的对象是单例，因此必须保证线程安全。

.. tip::

  非线程安全的功能（例如数据库连接等）会在Javadoc中明确标注其非线程安全。

Java17 Ready
--------------------------------------------------
Nablarch6的生产代码基于Java17，不使用Java18及以上版本提供的API。

这是为了保持对现有Nablarch6引入项目的向后兼容性。

不过，在使用Nablarch6开发应用时，只要使用Java17或更高版本即可，
Java18及以上版本提供的API也可以正常使用。

.. _nablarch_architecture-backward_compatible:

应用中可使用的API
--------------------------------------------------

Nablarch将预计在应用开发中需要的API定义为公开API。
公开API使用 :java:extdoc:`Published<nablarch.core.util.annotation.Published>` 注解标注，以便明确哪些类或方法属于公开API。

公开API是供应用使用的API，因此在版本升级时会保持向后兼容性，避免对应用造成修改影响。
但严重缺陷或安全漏洞修复时，可能无法保证向后兼容性。

关于字符串转BigDecimal时可能导致堆内存不足的问题
------------------------------------------------------------------
当将字符串转换为BigDecimal时，若指定指数表示法（例如值为 ``9e100000``）时，可能会发生以下问题：

* 调用 :java:extdoc:`BigDecimal#toPlainString() <java.math.BigDecimal.toPlainString()>` 时生成极长字符串，导致堆内存压力增大
* 使用 :java:extdoc:`DecimalFormat <java.text.DecimalFormat>` 格式化时生成极长字符串，导致堆内存压力增大

因此，Nablarch在将字符串转换为BigDecimal时，使用 :java:extdoc:`BigDecimal#scale <java.math.BigDecimal.scale()>`
进行位数检查，防止加载可能导致堆内存压力过大的大数值。
该功能将允许的scale范围限定在 ``-9999`` 到 ``9999`` 之间，若尝试转换超出此范围的指数表示值，则抛出异常以避免堆内存压力。

允许的scale范围可通过配置修改。
配置需在System Repository功能的环境配置文件中指定。
配置方法请参考 :ref:`repository-environment_configuration`。

例如，若希望允许的范围为 ``-10`` 到 ``10``，可添加如下配置：

.. code-block:: properties

  nablarch.max_scale=10

关于已弃用（Deprecated）API
------------------------------------------------------------------
Nablarch中以下API将标注 :java:extdoc:`@Deprecated <java.lang.Deprecated>` 注解，标记为已弃用：

* 已移动到其他包的类

  当因Nablarch团队原因将类移动到其他包时，原包中的类将被标记为已弃用。
  Javadoc中会注明应使用新位置的类。

  原包中的类会将所有处理委托给新包中的类，因此即使继续使用原类仍可正常运行。
  但不会新增方法等，建议使用新包中的类。

* 存在缺陷或安全问题的类或方法

  存在缺陷或安全问题的类将被标记为已弃用。
  Javadoc中会注明原因，以及推荐替代的API或实现方式。

  需参考Javadoc，使用已解决缺陷和安全问题的API进行应对。

  .. important::

   对于缺陷或漏洞，原则上会进行修复。
   但有时由于类结构限制或为保持向后兼容性，会保留有问题的API作为已弃用状态。
   若API被保留为已弃用，则即使将来发现新缺陷也不会再修复。
   因此，应用方必须使用已解决问题的新API进行替换。

.. tip::

  本文档中推荐使用替代功能的API，未被标记为已弃用（即未使用 :java:extdoc:`@Deprecated <java.lang.Deprecated>` 注解）。
  因为这些API（功能）本身使用无问题，即使存在缺陷，也会在版本升级时得到修复。
